
## E-CommerceService 프로젝트 개요
#### - 이 프로젝트는 높은 트래픽과 동시성 상황에서도 안정적인 주문, 결제 및 포인트 시스템을 제공하는 것을 목표로 진행하였습니다.
#### - TDD 기반으로 비즈니스 로직을 설계히고, 발생할 수 있는 동시성 이슈를 비관/낙관락 전략을 통해 해결하였습니다.

### 주요 비즈니스 프로세스 및 동시성 제어 전략
#### 1. 포인트 충전 (UserPoint)
* **프로세스** : 사용자 포인트 조회 -> 충전 금액 합산 -> 포인트 이력 저장
* **동시성 이슈**: 동일 사용자가 짧은 시간에 충전 버튼을 여러 번 클릭(일명 따닥)할 경우 중 복 충전 위험 존재.
* **해결책(낙관적 락)**
  * `User` 엔티티에 `@Version` 필드를 도입하여 낙관적 락 적용
  * 먼저 완료된 요청이 버전을 올리면, 뒤늦게 도착한 중복 요청은 버전 부일치로 실패 처리되어 자연스럽게 중복 결제 방지.

#### 2. 주문 및 결제 (Order & Payment)
* **프로세스** : 재고 확인 및 차감 -> 쿠폰 유효성 검증 -> 포인트 차감 -> 주문/결제 데이터 생성 -> 장바구니 상태 변경 -> 외부 플랫폼 전송
* **동시성 이슈** : 인기 상품의 경우 여러 사용자가 동시에 주문 시 실제 재고보다 더 많은 주문이 발생하는 '초과 판매' 위험.
* **해결책 (비관적 락)**:
  * `ProductRepository`에서 `findByIdWithPessimistickLock`을 통해 비관적 락 적용
  * DB 수준에서 해당 상품 레코드에 락을 걸어, 재고 차감 로직이 순차적으로 수행되도록 보장함.

### 테스트 전략 및 결과
#### 1. 단위 테스트 (Unit Test)
* `Mockito`를 사용하여 외부 의존성을 배제하고 순수 비즈니스 로직(할인 금액 계산, 상태 변경 등)을 빠르게 검증
* `Spy`를 활용하여 엔티티 내부의 상태 변경 메서드 호출 여부를 정밀하게 확인

#### 2. 동시성 및 통합 테스트
* **환경** : `Testcontainers`를 활용하여 실제 MySQL 8.0 컨테이너 환경에서 테스트를 수행하여 신뢰도를 높였습니다.
* **시나리오**:
  * ** 포인트 중복 충전**: `ExecutorService`와 `CountDownLath`를 사용하여 2개의 쓰레드가 동시에 충전을 시도했을 때, 1건만 성공하고 나머지는 실패하는지 검증.
  * ** 재고 차감 **: 100명의 사용자가 동시에 주문을 시도했을 때, 최종 재고가 정확하게 차감되는지 확인
